1.1

The domain object had no way to change its status

Blocker
domain/Notification.java
What I wrote
// Notification had a status field...
private NotificationStatus notificationStatus;

// ...and NotificationStatus had the rules...
public boolean canTransition(NotificationStatus next) { ... }

// ...but nothing ever called it. No method could change the status.
Corrected
public void transitionTo(NotificationStatus next, Instant now) {
    if (!notificationStatus.canTransition(next)) {
        throw new IllegalStateException(
                "Notification %s cannot move from %s to %s".formatted(notificationId, notificationStatus, next));
    }
    this.notificationStatus = next;
    this.updatedAt = now;
}

Why it was wrong: the whole lifecycle was dead code. Nothing could ever become QUEUED, SENT or FAILED, so the service and engine I write next would have had nothing to call. I had written the rules (in the enum) but not the door that uses them.

Concept: keep the rule next to the data it guards
The enum knows which moves are legal; the object applies them. Because notificationStatus is private and only transitionTo() can change it, no code anywhere can put a notification into an illegal state. That is encapsulation doing real work, not just "make fields private". Note also that now is a parameter instead of calling Instant.now() inside: that is what lets a test pass a fixed time and assert the exact updatedAt.

1.4

Argument order flipped: (content, title) in one place, (title, content) everywhere else

Bug
domain/Notification.java
What I wrote
public static Notification create(String userId, String content, String title, ...)
Corrected
public static Notification create(String userId, String title, String content, ...)

Why it was wrong: both are String, so the compiler cannot help. Swap them by accident and the SMS body becomes "Money debited" while the title becomes the whole message. It compiles, it runs, and the customer gets nonsense. Keeping one order everywhere is the only protection.

Concept: same-type parameters are a trap
When several parameters share a type, order mistakes are invisible to the compiler. Defences, in order of strength: keep a consistent order everywhere (done here), use a builder for long lists, or wrap values in small types (record Title(String value)) so a swap stops compiling.

1.6

The restore() builder could not restore the status

Blocker
domain/Notification.java
What I wrote
@Builder(builderMethodName = "restore")
public Notification(String notificationId, Instant updatedAt, ..., Instant cretedAt, String idempotencyKey) {
    // no notificationStatus parameter anywhere
}
Corrected
@Builder(builderMethodName = "restore")
private Notification(String notificationId, String userId, String title, String content,
                     NotificationType notificationType, NotificationPriority notificationPriority,
                     NotificationStatus notificationStatus, String idempotencyKey,
                     Instant createdAt, Instant updatedAt) { ... }

Why it was wrong: restore() exists to rebuild a notification read from the database. A row stored as SENT would come back with status == null, and the next transitionTo() would throw NullPointerException. Loading must reproduce the row exactly.

Concept: two doors in, for two different reasons
create(...) makes a new notification: it generates the id and forces the starting status. restore()...build() rebuilds an existing one: every field comes from the database, nothing is generated. Lombok's @Builder(builderMethodName = "restore") renames the generated builder() method, so the call site reads Notification.restore().userId("u1")...build(). A builder is used here because 10 positional arguments of mostly the same type are easy to mis-order (see 1.4).
1.7

Public constructors and no null checks

Bug
domain/Notification.java
What I wrote
public Notification(...) { this.userId = userId; ... }   // anyone can build any state
public Notification(...) { ... }                          // second public constructor
Corrected
private Notification(...) {
    this.userId = Objects.requireNonNull(userId, "userId");
    this.title = Objects.requireNonNull(title, "title");
    ...
    this.idempotencyKey = idempotencyKey;   // optional: null means "no deduplication"
}

Why it was wrong: a public constructor is a second, unguarded way in. Any code could create a notification with a null type or a status of its choosing, bypassing the rules in create(). Without the null checks, a null userId stays invisible until the database rejects the insert, far from the line that caused it.

Concept: fail fast
Objects.requireNonNull(x, "x") throws immediately, at the exact line, naming the field. The alternative is a NullPointerException or SQL error minutes later in a different class. Note which field is deliberately not checked: idempotencyKey is optional, and the comment says so, so the next reader does not "fix" it by adding a check.

1.9

DTOs with no getters: the API would send {} and read nothing

Blocker
dto/request/NotificationRequest.java · dto/response/NotificationResponse.java
What I wrote
public class NotificationRequest {
    @NotBlank @Size(max = 64)
    String userId;          // package-private field, no getter, no setter
    @NotNull
    NotificationType notificationType;
    ...
}
Corrected
public record NotificationRequest(
        @NotBlank @Size(max = 64) String userId,
        @NotBlank @Size(max = 200) String title,
        @NotBlank @Size(max = 2000) String content,
        @NotNull NotificationType notificationType,
        @NotNull NotificationPriority notificationPriority,
        @Size(max = 128) String idempotencyKey) {
}

Why it was wrong: Jackson (the JSON library Spring uses) looks for public getters, not package-private fields. The damage ran both ways:

  • Request: every field stayed null whatever the client sent, so validation rejected every request with "must not be blank". The endpoint could never succeed.
  • Response: nothing was visible to serialise, so the API would answer {} for every notification.
Both were silent: the code compiles perfectly.

Concept: record (Java 16+)
record X(int a, String b) {} generates the constructor, the accessors (a(), b(): no get prefix), plus equals, hashCode and toString. Fields are final, so a record is immutable. That makes it a perfect DTO: data in, data out, no behaviour. Jackson understands records natively. Validation annotations written on the components apply to the fields, so @NotBlank keeps working.

Use a record for DTOs and events. Use a normal class for Notification, because it has changing state (status) and rules to protect.

The retryable flag nobody could read

Blocker
exception/NotificationDeliveryException.java
What I wrote
public class NotificationDeliveryException extends RuntimeException {
    private final boolean retryble;                    // spelling, and...

    public NotificationDeliveryException(String message, boolean retyrable, Throwable cause) { ... }

    public static NotificationDeliveryException retryble(String message, Throwable cause) { ... }
    public static NotificationDeliveryException permanent(String message, Throwable cause) { ... }
    // ...no way to read the flag
Corrected
private final boolean retryable;

private NotificationDeliveryException(String message, boolean retryable, Throwable cause) { ... }

public static NotificationDeliveryException retryable(String message, Throwable cause) { ... }
public static NotificationDeliveryException permanent(String message, Throwable cause) { ... }

    return retryable;
}

Why it was wrong: the class exists to answer one question, "should we try again?", and it had no way to answer it. ExponentialBackoffRetryPolicy.isRetryable(failure) would not have compiled. The constructor was also public, so callers could sidestep the two named factories; making it private means retryable(...) and permanent(...) are the only ways to build one.

Concept: static factory + private constructor
NotificationDeliveryException.retryable("gateway timeout", cause) says what it means. new NotificationDeliveryException("gateway timeout", true, cause) forces the reader to guess what true refers to. Named factories plus a private constructor give a small, readable, impossible-to-misuse API.

ModifierWho can use it
publiceveryone

The rule of thumb here: NotificationDecorator's constructor is correctly protected, because only subclasses ever call it through super(wrapped). 2.2

Null check used in one class but not the others

Bug
decorator/NotificationDecorator.java · decorator/SimpleNotification.java
What I wrote
// SignatureNotificationDecorator: good
this.signature = Objects.requireNonNull(signature, "signature");

// NotificationDecorator: no check
protected NotificationDecorator(NotificationContent notificationContent) {
    wrapped = notificationContent;
}

// SimpleNotification: no check, and the fields are not final
private String title;
private String body;
Corrected
protected NotificationDecorator(NotificationContent wrapped) {
    this.wrapped = Objects.requireNonNull(wrapped, "wrapped");
}

private final String title;
private final String body;

public SimpleNotification(String title, String body) {
    this.title = Objects.requireNonNull(title, "title");
    this.body = Objects.requireNonNull(body, "body");
}

Why it was wrong: wrapped is the most important field in the whole pattern, and it was the one left unchecked. With a null wrapped object, construction succeeds and the NullPointerException appears later inside getBody(), one layer down the chain, where the stack trace points at the wrong class. The non-final fields in SimpleNotification are a smaller issue: a decorated message should never change after it is built, and final makes the compiler enforce that.

Concept: Objects.requireNonNull (you asked about this one)
public static <T> T requireNonNull(T obj, String message)
It returns the value if it is not null, and throws NullPointerException(message) if it is. Because it returns the value, it fits straight into an assignment: this.x = requireNonNull(x, "x").
  • Why not if (x == null) throw ...? Same behaviour, one line instead of three, and it is the standard idiom every Java reviewer recognises.
  • Why the message? Without it you get a bare NullPointerException with no field name. With it, the exception says wrapped, and you know exactly what was missing.
  • Where to put it: in the constructor, so a broken object can never exist. This is called failing fast: crash at the mistake, not three classes later.
  • When to skip it: for genuinely optional values. In Notification the idempotencyKey is deliberately not checked, because null is a valid value there ("no deduplication").
Related: Objects.requireNonNullElse(x, fallback) returns a default instead of throwing.

2.5

What was already right

Keep doing this
decorator/*.java
  • The pattern is correct: NotificationDecorator implements NotificationContent and holds a NotificationContent. That "is-a + has-a" pair is what lets decorators wrap each other endlessly.
  • The base class forwards both methods, so each decorator overrides only getBody() and the title passes through untouched. Verified by test.
  • protected final NotificationContent wrapped: subclasses can read it, nobody can swap it.
  • The timestamp is formatted in the constructor, not inside getBody(), so two calls always return the same text. This is a genuinely good decision, explained below.
  • DateTimeFormatter as private static final with an explicit Locale: exactly right, explained below.
Concept: DateTimeFormatter (you asked about this one)
private static final DateTimeFormatter FORMAT =
        DateTimeFormatter.ofPattern("dd MMM yyyy, HH:mm:ss z", Locale.ENGLISH);
It converts a date/time object into text (format) or text back into one (parse). Four things about the line you wrote, all of which you got right:
  • static final is correct. DateTimeFormatter is immutable and thread-safe, so one shared instance serves every request. Building a new one per call would be pure waste. (This is the big difference from the old SimpleDateFormat, which is not thread-safe: sharing one across threads silently produces corrupted dates. That class is a classic source of production bugs; DateTimeFormatter is its safe replacement.)
  • The pattern letters: dd = 2-digit day, MMM = short month name ("Sep"), yyyy = year, HH = hour 00-23 (hh would be 12-hour and need AM/PM), mm = minutes, ss = seconds, z = time-zone name ("UTC", "IST"). Case matters: MM is the month number, mm is minutes. Swapping them is a classic bug.
  • Locale.ENGLISH matters. MMM is translated using the locale. Without an explicit one, the JVM's default is used, so the same code could print "Sep" on your laptop and something else on a server configured differently. Passing the locale makes the output independent of where it runs.
  • z requires a zoned type. That is why the constructor takes a ZonedDateTime. An Instant or LocalDateTime carries no zone, and formatting one with z throws UnsupportedTemporalTypeException at runtime.
Why formatting in the constructor is the right call: if getBody() formatted the time each call, two calls a second apart would return different text, and the message saved in the database could differ from the one that was sent. Format once, store the String.

3.3

What was already right (including two things you got for free)

Keep doing this
retry/*.java
  • All validation in the constructor. A bad value in application.yml now fails at startup, not during a real outage at 2am.
  • The overflow guard. millis >= maxDelay.toMillis() is checked before the cast, so attempt 5000 returns the cap instead of a garbage value. Verified with Integer.MAX_VALUE.

Concept: pattern matching for instanceof (you asked about this one)
return failure instanceof NotificationDeliveryException delivery && delivery.isRetryable();
Java 16+ lets you declare a variable inside the instanceof check. It replaces three steps with one: 
// the old way
if (failure instanceof NotificationDeliveryException) {          // 1. test
    NotificationDeliveryException d = (NotificationDeliveryException) failure;   // 2. cast
    return d.isRetryable();                                      // 3. use
}
return false;
The variable delivery is called a pattern variable. Two rules make this line safe:
  • instanceof is false for null, always, without throwing. So a null failure short-circuits to false.
  • && short-circuits: the right-hand side runs only if the left side was true. That is what guarantees delivery is assigned before it is used. The compiler enforces this: with || instead of &&, the same line would not compile, because delivery would be in scope where the type check had failed.
Scope is exactly where the compiler can prove the test passed: after &&, or inside the if body. Related modern forms: case NotificationDeliveryException d -> ... in a switch, and record patterns like if (o instanceof Point(int x, int y)).
Concept: Duration and toMillis() (you asked about this one)
Duration is an immutable amount of time, stored internally as seconds + nanoseconds. Every method returns a new instance; nothing is ever modified in place.
CallDoes
Duration.ofSeconds(1).toMillis()→ 1000 (a long, unwrapped so you can do maths)
Duration.ofMillis(1500)builds a Duration from a number
d.isNegative() / d.isZero()the readable way to validate
a.compareTo(b) < 0"a is shorter than b" (Durations are Comparable, so no < operator)
Duration.ZEROthe shared zero-length constant

Why your code converts at all: you cannot multiply a Duration by 2.0. There is a multipliedBy(long), but the multiplier here is a double. So the line drops to plain numbers, does the maths, and converts back: 
double millis = initialDelay.toMillis() * Math.pow(multiplier, failedAttempt - 1);
...
return Duration.ofMillis((long) millis);
Two details worth knowing:
  • Math.pow returns double, and a huge exponent gives Double.POSITIVE_INFINITY instead of wrapping around to a negative number. Comparisons against Infinity still work, which is why your cap check saves the day.
  • The (long) cast truncates, it does not round: (long) 149.9 is 149. Harmless for a retry delay; dangerous if you ever do the same with money. For money, use BigDecimal, never double.
Also remember Thread.sleep() takes milliseconds, which is why the engine will call delay.toMillis() again later.

Concept: @Slf4j and logging (you asked about this one)
@Slf4j
public class EmailNotificationChannel implements NotificationChannel { ...
    log.info("[EMAIL] delivered notification {} to the user {}", id, userId);
What the annotation does: at compile time Lombok inserts exactly one line for you: 
private static final org.slf4j.Logger log =
        org.slf4j.LoggerFactory.getLogger(EmailNotificationChannel.class);
That is all. The variable is called log, which is why you can use it without declaring anything. static final matters: one logger per class, shared by every instance, created once.
  • SLF4J is a facade, not a logging library. Your code talks to the SLF4J API; the actual writing is done by whatever implementation is on the classpath, which for Spring Boot is Logback. Swap the implementation and not one line of your code changes. (Same idea as your NotificationChannel interface: code against the abstraction.)
  • Why {} instead of +: with log.debug("x " + expensive()) the string is built every time, even when debug logging is off. With log.debug("x {}", expensive()) the formatting happens only if the level is enabled. It also keeps the message text constant, which lets log tools group identical messages.
  • Levels, from noisiest to most serious: trace, debug, info, warn, error. Rule of thumb: info = a normal business event worth keeping ("delivered"), warn = recoverable trouble (a retry), error = something that needs a human. Set the threshold in application.yml: logging.level.org.example.notificationservice: DEBUG.
  • Exceptions go last, with no {}: log.error("failed for {}", id, ex) prints the full stack trace. Writing ex.getMessage() instead throws away the stack trace, which is the part you actually need.
  • Never log secrets. OTPs, passwords, full card or account numbers. This is why your channels log the id and user but not the content.
  • Alternative logger name: LoggerFactory.getLogger("NOTIFICATION_AUDIT") creates a logger with a name of your choosing rather than the class name, so logback can route those lines to a separate file. You will want that in NotificationAuditListener next round.
Why not System.out.println: no timestamp, no level, no logger name, no thread, cannot be filtered or switched off, and it does not go to the log file the ops team reads.
