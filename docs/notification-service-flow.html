The one-paragraph version

The banking system POSTs a notification request. NotificationController passes it to NotificationService, which validates it, checks whether this exact event was already notified (idempotency), builds the final message text with the decorators, saves it as CREATED and announces that. It then asks the preference service whether the customer accepts this channel (unless the notification is CRITICAL, which overrides preferences). If allowed, it marks the notification QUEUED and hands it to the NotificationEngine. The engine asks the resolver for the channel that handles this type, tries to send, and on failure asks the retry policy whether to try again. Every status change is written to the database and announced to the listeners (audit, logging, metrics).

NotificationService: the six steps

The service never sends anything itself. It asks six collaborators, in this order.

1

Validate the request

Uses: Validator

Run the bean-validation constraints on NotificationRequest (@NotBlank, @Size, @NotNull). If anything fails, throw InvalidNotificationRequestException carrying all the violations at once.
Why in the service, not the controller? Later, Kafka consumers will call send() directly without any HTTP involved. Validation in the service means every caller gets the same checks. The GlobalExceptionHandler turns the exception into 400 for HTTP callers.
2

Idempotency: have I already sent this?

Uses: repository.findByIdempotencyKey(key)

If the key is present and a notification already exists for it, return that one and stop. No new row, no second SMS, no events. Treat a blank key (" ") as "no key".
The race: two identical requests can both find nothing. The database's unique constraint rejects the second insert, the repository turns that into DuplicateIdempotencyKeyException, and the service catches it in step 4 and returns the winner. Checking in Java alone is not enough.
3

Build the final text with the decorators

Uses: SimpleNotification → TimestampNotificationDecorator → SignatureNotificationDecorator, plus clock

NotificationContent content = new SimpleNotification(request.title(), request.content());
content = new TimestampNotificationDecorator(content, ZonedDateTime.now(clock));
content = new SignatureNotificationDecorator(content, signature);
Order matters: decorate before saving, so the database stores exactly the text the customer received. Save content.getBody(), never the raw request body.
4

Create, save, announce

Uses: Notification.create(...), repository.save, eventPublisher

create() generates the UUID and sets CREATED. Save it, then publish NOTIFICATION_CREATED so audit, logging and metrics all hear about it.
Order again: save first, publish second. Announcing something that failed to save would put a lie in the audit trail.
5

Preferences, with the banking override

Uses: preferenceService.isChannelEnabled(userId, type), priority.overridesUserPreferences()

boolean allowed = notification.getNotificationPriority().overridesUserPreferences()
        || preferenceService.isChannelEnabled(userId, type);
If not allowed: transition to CANCELLED, persist, publish NOTIFICATION_CANCELLED with a reason, and return without calling the engine.
Why the override: a customer may switch off marketing SMS, but an OTP, a suspicious-transaction alert or a card block must still reach them. That is what CRITICAL means here.
6

Queue it and hand over

Uses: repository.updateStatus, engine.deliver(notification)

Transition to QUEUED, persist, then call the engine. The service's job ends here; everything after this belongs to the engine.
Why not @Transactional on this method? The engine may sleep for seconds between retries. Holding a database transaction (and its connection) open that whole time would exhaust the pool under load. Each status write commits on its own.

NotificationEngine: the attempt loop

channel = resolver.resolve(type)          // no channel? -> FAILED, stop

for (attempt = 1; ; attempt++) {
    status = PROCESSING                    // persisted every time
    failure = trySend(channel)             // returns the exception instead of throwing

    if (failure == null) {
        status = SENT;  publish(SENT);  return
    }

    keepGoing = attempt < maxAttempts && retryPolicy.isRetryable(failure)
    if (!keepGoing) {
        status = FAILED;  publish(FAILED, reason);  return
    }

    status = RETRYING;  publish(RETRYING, reason)
    sleep(retryPolicy.delayAfterAttempt(attempt))   // interrupted -> FAILED, stop
}
The two rules that keep it safe The SENT write happens outside the try/catch, so a database error cannot be mistaken for a send failure and trigger a second SMS. And every RuntimeException is caught, not just NotificationDeliveryException, so a bug inside a channel cannot strand a notification in PROCESSING.

SENTEngineChannel accepted it. Terminal.
FAILEDEnginePermanent failure, attempts exhausted, or no channel. Terminal.

Rule: only Notification.transitionTo() may change status, and it rejects any move the enum does not allow. SENT, FAILED and CANCELLED are terminal: nothing leaves them.

Five traced scenarios

A. Happy path — SMS delivered first try
  1. Request validated
  2. Key txn-9001:debit not seen before
  3. Text built: body + Time: ... + signature
  4. Saved CREATED, event NOTIFICATION_CREATED
  5. SMS enabled for this user → allowed
  6. QUEUED → engine → PROCESSING → channel accepts → SENT, event NOTIFICATION_SENT
Result: HTTP 201, 4 database writes, 2 events.
B. The banking system retries the same event
  1. Request validated
  2. Key txn-9001:debit found → return the existing notification immediately
Result: no new row, no events, no second SMS. Steps 3-6 never run.
C. Customer switched off SMS
  1. Steps 1-4 as usual: saved CREATED, event published
  2. Priority is HIGH, not CRITICAL; SMS disabled → not allowed
  3. CANCELLED, event NOTIFICATION_CANCELLED, engine never called
Same request with CRITICAL priority (an OTP): the preference check is skipped and it is delivered.
D. Gateway timeout, then success
  1. Engine: PROCESSING → channel throws retryable("gateway timeout")
  2. Attempts left and retryable → RETRYING, event NOTIFICATION_RETRYING, sleep 500ms
  3. PROCESSING again → channel accepts → SENT
Result: 6 database writes, 2 events, one customer message. The retry is invisible to the customer.
E. Invalid phone number
  1. Engine: PROCESSING → channel throws permanent("invalid number")
  2. Not retryable → straight to FAILED, event NOTIFICATION_FAILED carrying the reason
Result: one attempt only. Retrying a wrong number three times helps nobody.

Each event reaches all three listeners: audit (compliance record), logging (operations) and metrics (counters). None of them can break delivery, because publish() catches whatever a listener throws.

60-second revision

  • Service = orchestration, engine = delivery. The service decides whether, the engine handles how.
  • Six steps: validate → idempotency → decorate → save + announce → preferences → queue + hand over.
  • Idempotency needs both a lookup in Java and a unique constraint in the database.
  • Decorate before saving, so the stored text is what the customer got.
  • CRITICAL beats preferences. OTPs and fraud alerts always go out.
  • Engine loop: PROCESSING → send → SENT, or ask the policy → RETRYING + wait, or FAILED.
  • SENT is written outside the try/catch, so a DB error cannot cause a duplicate send.
  • Every status change is persisted and announced. Statuses are state; events are news.
  • Terminal states: SENT, FAILED, CANCELLED. Nothing leaves them.
  • Nothing is @Transactional across a send, because retries sleep.
