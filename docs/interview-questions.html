0 · Pitching the project

The first question is always "tell me about it". Have two versions ready.

30 seconds

"It is the notification microservice for a digital banking system. Other services send it a request — an OTP, a debit alert, a card block — and it delivers that through the right channel: email, SMS, push or in-app. It is built around three patterns: Strategy for the channels, Observer for audit and metrics, Decorator for the message text. It has idempotency so the same bank transaction never notifies twice, and a retry policy with exponential backoff for transient failures."

2 minutes (add this)

"A request comes in over REST. The service validates it, checks the idempotency key so a retried bank event does not produce a second SMS, builds the final text with decorators that add a timestamp and the bank's signature, saves it, and checks the customer's channel preferences — although CRITICAL notifications like OTPs override those. Then a separate engine does the delivery: it resolves the right channel from a map, sends, and on a transient failure retries with exponential backoff. Every status change is persisted and published as an event to three listeners: audit, logging and metrics. The domain model is kept free of JPA, so persistence sits behind a repository interface."

Say this at the end
"Two things I would add next: the recipient lookup, because the service only knows a user id today, and moving delivery off the request thread so retries do not block the caller." Naming your own gaps reads as senior.

1 · Design patterns

The core of the interview, because the project is built on three of them.

1.1Which design patterns did you use and why?Basic

Three, each answering a different question:

  • Strategy — "which implementation should send this?" One class per channel behind NotificationChannel.
  • Observer — "something happened, who needs to know?" Audit, logging and metrics listeners.
  • Decorator — "how do I add behaviour to an object without changing its class?" Timestamp and signature layered onto the message.
1.2How does Strategy remove the if/else?Common

Each channel declares which type it handles via supportedType(). Spring injects every NotificationChannel bean into the resolver as a List, and the resolver builds an EnumMap<NotificationType, NotificationChannel> once in its constructor. Delivery is then a map lookup. Adding WhatsApp means one new class and one new enum value — the engine does not change.

Follow-up: "What if two channels claim the same type?" → The resolver throws in the constructor, so the application refuses to start rather than silently picking one.
1.3Why Decorator and not just a helper method that appends text?Common

Because the additions are optional and composable. With decorators I can have timestamp only, signature only, both, or later a masking decorator, in any order, chosen at runtime from config. A helper method would need a boolean parameter per feature, and subclassing would need one class per combination.

Follow-up: "What makes it a Decorator and not just wrapping?" → The decorator implements the same interface as the thing it wraps. That is what lets it be used anywhere the original was, including inside another decorator.
1.4Why did you not use Observer to choose the channel?Deep

Because they answer different questions. Observer broadcasts to everyone interested and ignores return values; delivery needs exactly one handler and must know whether it succeeded. Using Observer there would mean every channel sees every notification and each one decides whether to act — scattered logic, no single place that knows what happened.

1.5Spring already has an event system. Why write your own Observer?Deep

Honest answer: for this project it was to implement the pattern explicitly. In production I would use ApplicationEventPublisher with @EventListener, which gives async handling via @Async and transaction-bound events via @TransactionalEventListener for free. My version is about thirty lines and swapping it would touch only the publisher.

Why this answer works
Interviewers like candidates who know the framework alternative and can justify the choice, instead of pretending the hand-rolled version is automatically better.
1.6Is your resolver a Factory?Common

Strictly it is a registry: it does not create channels, Spring does, it looks one up by key. It sits in a package called factory because it plays the "give me the right implementation" role a factory usually plays. A real factory would new the object per call.

1.7Which other patterns appear in the code without being named?Deep
  • Repository (and Ports & Adapters): the domain depends on NotificationRepository, the JPA implementation sits behind it.
  • Facade: NotificationService is one entry point over six collaborators.
  • Builder: Notification.restore() for rebuilding from the database.
  • State machine: NotificationStatus.canTransition().
  • Template-method-ish: NotificationDecorator forwards by default, subclasses override one method.

2 · OOP and SOLID

2.1Show me SOLID in your code.Common
  • S — the service orchestrates, the engine delivers, channels send, listeners react. Each has one reason to change.
  • O — a new channel is a new class; no existing class is edited.
  • L — any NotificationChannel works wherever the interface is used; decorators are usable wherever NotificationContent is.
  • I — NotificationPreferenceService exposes only isChannelEnabled; the setter lives on the implementation.
  • D — the service and engine depend on interfaces (repository, retry policy, preferences), never on JPA or a concrete channel.
2.2Why is Notification a class but NotificationRequest a record?Common

Notification has changing state (status, updatedAt) and rules that protect it, so it needs a private constructor, a factory and transitionTo(). A record is immutable with public accessors, which is perfect for a DTO that only carries data across a boundary.

2.3Why not expose the entity directly from the controller?Basic

Three reasons: it would leak database structure into the API contract, so a column rename becomes a breaking API change; it can expose fields clients should not see; and JPA entities can be lazy-loaded proxies that blow up during serialisation. The DTO decouples the two.

2.4Why is the status change a method on the domain object rather than a setter?Deep

A setter would let any code put the object into an impossible state, like moving SENT back to PROCESSING. transitionTo() consults the state machine and throws on an illegal move, so the rule lives with the data it guards. That is encapsulation doing real work rather than just hiding a field.

3 · Core Java

3.1Why EnumMap instead of HashMap?Common

Its keys are enum constants, so internally it is an array indexed by ordinal(): no hashing, no collisions, less memory, and iteration in enum declaration order. EnumSet is the same idea, storing membership as bits in a long.

3.2Why EnumType.STRING on the entity?Common

The default is ORDINAL, which stores the enum's position. Insert a new constant in the middle later and every existing row silently means something different. STRING stores "EMAIL", so reordering is harmless.

Bonus: I also pin the column to varchar, because Hibernate would otherwise generate a MySQL ENUM(...) column, and ddl-auto=update never alters it when a new value is added.
3.3Explain this line: failure instanceof NotificationDeliveryException d && d.isRetryable()Common

Pattern matching for instanceof, Java 16+: it tests the type and declares the cast variable in one step. It is safe because instanceof is false for null, and && short-circuits, so d is only used when the test passed. With || it would not compile.

3.4What is a functional interface, and where is one in your code?Basic

An interface with exactly one abstract method, so a lambda can implement it. NotificationEventListener is one: tests pass event -> list.add(event) where a listener is expected.

3.5Why inject a Clock instead of calling Instant.now()?Deep

Testability. With a Clock bean, production uses the real clock and tests use Clock.fixed(...), so I can assert the exact timestamp inside a decorated message or an event. Calling Instant.now() directly makes time an invisible global dependency.

3.6Checked or unchecked exceptions, and why?Common

All mine are unchecked. A checked exception forces every layer in between to declare or wrap it, which pollutes signatures for errors those layers cannot fix. Spring's own data and web exceptions are unchecked for the same reason. Where recovery is genuinely possible, I encode it as data instead: the retryable flag on NotificationDeliveryException.

4 · Concurrency

4.1Why CopyOnWriteArrayList for the listeners?Common

Listeners are written once at startup and read on every publish. That list copies the array on each write and needs no lock for reads, so publishing is cheap and iteration can never throw ConcurrentModificationException even if someone subscribes mid-publish.

4.2Why LongAdder and not AtomicLong or long?Deep

long++ is read-modify-write, so concurrent increments are lost. AtomicLong is correct but every thread contends on one memory location. LongAdder spreads increments across internal cells and sums them on read: much faster under contention, at the cost of a slightly more expensive read. Counters are the textbook case for it.

4.3Why ConcurrentHashMap.compute() in the preference service?Deep

Because get-modify-put is a race: two threads disabling two different channels for the same user would each read the same set and one write would erase the other. compute() runs the update atomically for that key, while other keys stay unblocked. Returning null also removes the entry, so the map cleans itself up.

Follow-up: "Why build a new EnumSet inside instead of mutating?" → Because reads happen without a lock. Replacing the value means a reader holding the old set still sees a consistent snapshot.
4.4Is your engine thread-safe?Deep

The engine itself holds no mutable state — only final collaborators — so it is safe to share. The Notification object it mutates belongs to one request. What is not protected is two servers processing the same notification at once; that needs optimistic locking with @Version, which I would add when delivery moves to a queue.

5 · Spring

5.1Constructor injection or field injection?Basic

Constructor, always. Dependencies become final, the object cannot exist half-built, missing dependencies fail at startup, and the class can be unit-tested with plain new. Field injection hides dependencies and needs reflection to test.

5.2How does Spring inject a List<NotificationChannel>?Common

It collects every bean of that type. That is what makes the resolver extensible: mark a new channel @Component and it joins the list automatically. Order can be controlled with @Order, but my resolver does not care because each channel declares its own key.

5.3@Component vs @Service vs @Repository?Basic

All three register a bean. @Service and @Repository are specialisations that document intent — with one real difference: @Repository enables exception translation, converting vendor SQL exceptions into Spring's DataAccessException hierarchy.

5.4Why is send() not @Transactional?Deep

Because delivery happens inside it, and retries sleep for seconds. A transaction spanning that would hold a database connection the whole time and exhaust the pool under load. Each status write commits on its own, which I accept: it means status is durable at every step, and a crash leaves a visible PROCESSING row rather than a rolled-back mystery.

Follow-up: "What would you do instead?" → Commit the notification in a short transaction, then publish to a queue and deliver in a separate consumer, so the database work and the network call are never in the same unit.
5.5How do exceptions become HTTP responses?Common

A @RestControllerAdvice class with @ExceptionHandler methods returning ProblemDetail, Spring's RFC 9457 implementation. Validation failures map to 400 with the list of violations, unknown ids to 404. Internal exceptions like NotificationDeliveryException never reach it, because the engine handles them.

6 · Database and JPA

6.1Why two classes, Notification and NotificationEntity?Deep

So the domain model has no JPA annotations and no persistence rules. The entity is the table shape; the mapper converts. It costs one extra class and buys a domain object I can unit-test with no database, plus freedom to change the schema without touching business logic.

Honest counterpoint to offer: for a small CRUD service this is over-engineering; one annotated class would do. It pays off when the domain has real behaviour, as it does here.
6.2Why a repository interface when Spring Data already gives you one?Common

So the service and engine depend on my vocabulary, not Spring Data's, and so the domain object never crosses into JPA types. The adapter also translates persistence errors into domain exceptions, like turning a unique-constraint violation into DuplicateIdempotencyKeyException.

6.3Why a targeted updateStatus query instead of save()?Deep

It writes exactly two columns, so it cannot accidentally overwrite other fields with a stale in-memory copy, and it is one small UPDATE rather than a select-then-merge. It also returns the affected row count, which lets me detect a missing notification.

6.4What indexes does this table need?Common

A unique index on idempotency_key — it enforces correctness, not just speed — and a plain index on user_id for the inbox query. The primary key covers lookup by id. At scale I would also index status plus created_at for retry sweeps and reporting.

6.5Would you use ddl-auto: update in production?Common

No. It is convenient in development but it never drops or alters existing columns, and it gives you no review or rollback. Production should use versioned migrations with Flyway or Liquibase, with ddl-auto: validate to catch drift.

7 · Reliability

This section separates a student project from a banking one. Know it cold.

7.1What is idempotency and how did you implement it?Common

Doing the same operation twice has the same effect as doing it once. The caller sends a key derived from the business event, such as txn-9001:debit. The service looks it up and returns the existing notification if found. The unique constraint on the column is the real guarantee: if two identical requests race, the database rejects the second insert and the service returns the winner.

Follow-up: "Why not just check in Java?" → Two threads (or two servers) can both see "not found" before either inserts. Only the database can arbitrate.
7.2Why exponential backoff rather than retrying immediately?Common

If a provider is overloaded, immediate retries add load and make it worse. Growing delays give it time to recover and spread our own load out. The cap stops delays growing without limit.

Follow-up they love: "What is missing?" → Jitter. With fixed backoff, a thousand notifications that failed together retry together. Randomising the delay spreads the herd.
7.3Who decides whether a failure is retryable?Deep

The channel, because only it knows the difference between a gateway timeout and an invalid phone number. It throws NotificationDeliveryException.retryable(...) or .permanent(...), and the policy reads the flag. Unknown runtime exceptions are treated as permanent: they are bugs, and retrying a bug just fails three times.

7.4What happens if the service crashes mid-delivery?Deep

Today the notification is left in PROCESSING and nothing resumes it — an honest limitation. The fix is a scheduled sweep that finds rows stuck in PROCESSING or RETRYING past a timeout and re-queues them, which works precisely because every status change is persisted as it happens.

7.5At-least-once or at-most-once delivery?Deep

At-least-once at the channel level: a provider may have accepted the message even if our call timed out, so a retry can duplicate it. Idempotency protects against duplicate requests, not duplicate sends. Making sends idempotent needs a provider-side idempotency key, which most SMS and email gateways support.

7.6How do you stop a broken listener from breaking delivery?Common

Each listener call in publish() is wrapped in its own try/catch. A listener that throws is logged and the loop continues, so a metrics bug cannot stop an SMS. I have a test with a deliberately broken listener that proves the other two still run.

8 · Testing

8.1How did you test the engine?Common

With a hand-written fake channel scripted to fail a given number of times, a mocked repository that records the status at every call, and a real publisher with a recording listener. Then I assert three things: how many times the channel was called, the exact sequence of persisted statuses, and the exact list of published events. A zero-delay retry policy keeps it instant.

Follow-up: "Mock or fake?" → Fake for the channel, because "fail twice then succeed" reads better as real code; mock for the repository, because I only care that it was called with the right state.
8.2How do you test something that sleeps?Deep

Inject the retry policy, then pass one with zero delays in tests. The waiting is a collaborator's decision, not the engine's. I keep one slower test that uses a real 200ms delay to prove the engine actually waits.

8.3Unit tests or integration tests for the repository?Common

Integration, with @DataJpaTest against in-memory H2, because the things worth testing are the mapping, the unique constraint and the update query — none of which a mock can verify. For production-grade confidence I would use Testcontainers with real MySQL, since H2 does not reproduce every MySQL behaviour.

8.4Which bug did your tests catch that review missed?Common

Several, and they make a good story. The best one: in the event publisher I wrote listeners.addAll(listeners), forgetting this., so the parameter was added to itself and the field stayed empty. It compiled, started fine, and silently notified nobody — no audit trail at all. A test that published an event and asserted the metrics counter caught it immediately.

Why to tell this story
It shows you test behaviour rather than structure, and that you understand why a silent failure is worse than a crash.

9 · Scaling it up

"How would you improve this?" is almost guaranteed. Have four answers ready.

9.1Delivery blocks the HTTP request. How would you fix that?Deep

Persist the notification, return 202 Accepted immediately, and publish it to a queue — Kafka here, since the banking system already uses it. A consumer runs the engine. The caller is no longer held for the length of the retries, and delivery workers scale independently of the API.

9.2How would you handle 10,000 notifications per second?Deep
  • Queue-based delivery with many partitions, keyed by user id so one user's messages stay ordered.
  • Batch the provider calls where the API allows it.
  • Rate-limit per provider, with a circuit breaker so a dead provider fails fast instead of consuming threads.
  • Move counters to Micrometer and Prometheus rather than in-memory.
  • Partition or archive the notifications table by date.
9.3What happens to notifications that fail permanently?Common

Today they are stored as FAILED with a reason and counted. Next step is a dead-letter topic plus an alert when the failure rate for a channel crosses a threshold, because a spike usually means the provider is down rather than the numbers being wrong.

9.4What is the biggest weakness of your design?Deep

The service has no recipient. It knows a userId but not an email address or phone number, so the channels are simulated. I would add a RecipientResolver that looks up contact details, cached, and treat a missing address as a permanent failure. Second weakness: no authentication, so the GET-by-user endpoint would leak other customers' notifications.

Never say "nothing"
Naming a real weakness, with the fix, is one of the strongest signals you can give. Saying the design is perfect is one of the weakest.

10 · Trap questions

Questions designed to see whether you understand your own code or just typed it.

10.1Why is the SENT status saved outside the try/catch?Deep

Because inside it, a database error while saving SENT would be caught as if the send had failed, and the engine would retry — sending the customer a second SMS. The send and the record-keeping must fail independently.

10.2Why catch RuntimeException and not just your own exception?Deep

Because a channel might throw a NullPointerException from a bug. If I only caught my own type, that would escape the engine and leave the notification stuck in PROCESSING forever. Catching everything means it ends as FAILED with the reason recorded.

10.3Your event has no message body. Is that an oversight?Common

Deliberate. Listeners write to logs, and a bank notification body contains OTPs, balances and account numbers. The event carries ids, type, status and a failure reason — enough to audit, impossible to leak.

10.4Why does CRITICAL ignore user preferences? Is that legal?Common

It is the normal distinction between marketing and transactional or security messages. A customer can opt out of promotions; they cannot opt out of an OTP or a fraud alert, because those are part of operating the account safely. The rule lives on the priority enum, so it is applied in exactly one place.

10.5What if two channels return the same supportedType()?Common

The resolver detects it while building its map and throws, so the application fails to start with a message naming both classes. Failing at startup is much better than silently picking whichever bean Spring happened to create first.

10.6Walk me through what happens when the SMS provider is down for 10 minutes.Deep

Each notification tries three times over about 1.5 seconds, then goes to FAILED with the reason, and the metrics counter for failures climbs. Nothing retries later, which is the gap: with a queue and a dead-letter topic those messages could be replayed once the provider recovers. A circuit breaker would also stop us wasting threads on a provider we know is down.

11 · Questions to ask them

Interviews end with "any questions?". These show engineering judgement rather than curiosity about perks.

  • "How do you handle idempotency and retries between your services today?"
  • "Is delivery synchronous anywhere in your stack, or is everything queue-based?"
  • "How do you manage schema migrations — Flyway, Liquibase, something in-house?"
  • "What does your testing pyramid look like? Do you use Testcontainers for database tests?"
  • "How do you monitor a failure like an SMS provider going down — who gets paged and how fast?"
  • "How much of the codebase is covered by automated tests, and is that enforced in CI?"
  • "What does the first month look like for someone joining this team?"
Three rules for the whole interview
  • Answer in two levels. Give the short answer, then stop. Let them ask for depth: it turns a monologue into a conversation.
  • Say "I do not know" when you do not. Follow it with how you would find out. It costs far less than bluffing, which they will detect.
  • Talk about trade-offs, not rules. "I chose X because Y, and the cost is Z" beats "X is best practice" every time.
