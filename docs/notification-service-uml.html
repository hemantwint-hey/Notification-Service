1Big picture

Which package talks to which. The controller only talks to the service. The service orchestrates, the engine delivers, and the three patterns each sit in their own corner.

Strategy: which implementation?Engine asks the resolver for the channel that matches the type. No if/else.
Observer: who needs to know?Service and engine announce events; audit, logging and metrics react independently.
Decorator: add behaviour by wrappingTimestamp and signature are layered onto the message text without subclass explosions.

What happens, in order, when the banking system calls POST /api/v1/notifications. alt boxes are if/else branches, loop is the retry loop. Words in [BRACKETS] are the status saved at that step.

3Strategy pattern: delivery channels

Strategy"I need to send this. Which implementation should do it?"
Why the resolver removes the switch Spring injects every NotificationChannel bean as a List. The resolver loops once in its constructor and builds Map<NotificationType, NotificationChannel> using each channel's supportedType(). After that, resolve(type) is just map.get(type).
Adding WhatsApp later
  • Add WHATSAPP to NotificationType
  • Create WhatsAppNotificationChannel implements NotificationChannel with @Component
  • Engine, resolver and other channels: zero changes (Open/Closed principle)

4Observer pattern: notification events

Observer"Something happened. Who needs to know?"

At runtime: one publish, every listener called

Send a snapshot, not the NotificationNotificationEvent copies the fields listeners need. A listener can't accidentally change the real notification's status.
Isolate listener failuresWrap each onEvent call in try/catch inside publish(). A broken metrics listener must never stop an SMS.
Never log the contentThe body can contain an OTP or balance. The event deliberately has no title/content field.

5Decorator pattern: message enrichment

Decorator"I have an object. How do I add behaviour without changing its class?"

The two lines between NotificationDecorator and NotificationContent are the heart of the pattern: a decorator is a NotificationContent (triangle) and has a NotificationContent inside it (diamond). That's why decorators can wrap each other.

At runtime: layers of an onion

SignatureNotificationDecorator
getBody() = inner.getBody() + signature
TimestampNotificationDecorator
getBody() = inner.getBody() + time line
SimpleNotification
getBody() = original body (call stops here)

Calling getBody() on the outside travels inward to SimpleNotification, then each layer appends its part on the way back out.

NotificationContent content =
        new SimpleNotification(title, body);

content = new TimestampNotificationDecorator(content, now);
content = new SignatureNotificationDecorator(content, signature);

String finalBody = content.getBody();

Result of content.getBody()

INR 5,000.00 debited from A/c XX1234.

Time: 16 Sep 2026, 10:15:32 UTC

- Enterprise Digital Bank. Never share your OTP.
Decorate the text, not the entity Only NotificationContent (title + body) gets wrapped. Save the final string into Notification.content. JPA can't persist a chain of wrapper objects.

6Core classes: service, engine, domain, retry, preferences

The orchestration layer. Note the service and engine depend on interfaces (NotificationRepository, NotificationPreferenceService, RetryPolicy), never on the concrete classes.

NotificationService does

  1. Validate the NotificationRequest
  2. If idempotencyKey was used before → return that notification
  3. Build the text with the decorators
  4. Notification.create(...) → save [CREATED] → publish event
  5. Check preferences (skipped for CRITICAL) → [CANCELLED] or [QUEUED]
  6. Hand over to engine.deliver(notification)

NotificationEngine does

  1. resolver.resolve(type) to get the channel
  2. [PROCESSING] → channel.send(notification)
  3. Success → [SENT] + publish
  4. Failure → ask RetryPolicy: retryable and attempts left?
  5. Yes → [RETRYING], wait delayAfterAttempt(n), go to step 2
  6. No → [FAILED] + publish
Exponential backoff in numbers With initialDelay = 500ms, multiplier = 2, maxDelay = 5s, maxAttempts = 3: attempt 1 fails → wait 500ms → attempt 2 fails → wait 1s → attempt 3 fails → FAILED. Formula: min(initialDelay × multiplierattempt-1, maxDelay).

7Persistence: keeping JPA out of the logic

Service and engine only see NotificationRepository and the plain Notification domain class. Everything JPA (@Entity, Spring Data) lives behind JpaNotificationRepository, which converts between the two.

Why two "Notification" classes? Notification (domain) has behaviour like transitionTo() and no JPA annotations. NotificationEntity is just the table shape. Swap MySQL for Mongo later and only the repository.jpa package changes.
Idempotency needs the database Two identical requests at the same instant can both pass findByIdempotencyKey(). Put a unique constraint on idempotency_key; when the insert fails, throw DuplicateIdempotencyKeyException and let the service return the existing row.

9Exceptions: who throws, who catches

Only two exceptions ever reach the API client. The other three are handled inside the service and engine.

ExceptionThrown byCaught by → result
InvalidNotificationRequestExceptionNotificationService (validation)GlobalExceptionHandler → 400 Bad Request
NotificationNotFoundExceptionNotificationService.getById, repository.updateStatusGlobalExceptionHandler → 404 Not Found
DuplicateIdempotencyKeyExceptionJpaNotificationRepository.save (unique constraint)NotificationService → returns the existing notification
NotificationDeliveryExceptionAny channel's send()NotificationEngine → RETRYING or FAILED (uses isRetryable())
UnsupportedNotificationChannelExceptionNotificationChannelResolver.resolveNotificationEngine → FAILED

11Open decisions

Not drawn above because you haven't chosen yet. Both change the entity, so decide before step 8.

Where do email address and phone number come from? Notification only has userId. Either the request carries the recipient, or add a RecipientResolver interface that the channels call to look up contact details by userId.
One channel or many per request? A money transfer often goes out as SMS + email + push. Today that's 3 requests with 3 idempotency keys. The alternative is Set<NotificationType> in the request, which produces one Notification per channel.
